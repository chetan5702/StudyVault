# StudyVault first working application

## Audit

The starting repository had FastAPI endpoints and SQLite data, but a Vite starter frontend. Startup created tables and seeded predictable demo credentials. Two authentication tests modified the real database. Uploads trusted browser MIME types, wrote unbounded files, exposed paths, stored zero sizes and omitted unit/group validation. Empty-account dashboards dereferenced a missing exam. Timestamps were naive.

## Implemented scope

1. Configuration and authentication: production secret validation, opt-in development-only seeding, direct bcrypt without passlib, hardened JWT validation, inactive-account checks, database-backed login throttling, verified email and enumeration-safe password recovery with account delivery after the generic response. Single-use account tokens are stored as digests; password reset increments the account token version so older JWTs stop working.
2. Persistence and integrity: frozen Alembic baseline, explicit initialization with schema validation for non-destructive legacy adoption, isolated test databases, UTC-aware timestamps including legacy SQLite reads, and SQLite foreign-key enforcement on every connection. Subject and profile writes validate the resulting college/course relationship, task PATCH is genuinely partial, and the misleading per-exam reminder field is rejected in favor of global reminder preferences.
3. Migration chain: revision `0003` adds Sreenidhi University idempotently; `0004_security_limits` adds persistent login throttling and backfilled per-owner storage usage; `0005_account_security` adds verified-account state, revocable JWT versions and expiring one-time tokens; `0006_archived_exam_subjects` adds immutable exam subject name/code snapshots, makes the archived exam subject link nullable and rejects a null subject on active exams. The existing database was backed up at revision `0005`, migrated to `0006`, and verified with all 51 pre-existing rows preserved and no foreign-key violations.
4. Secure files: bounded multipart reception and streamed writes, PDF/image/DOCX parsers, random storage names, accurate sizes, hidden storage keys, atomic cumulative quota reservations, an atomic one-winner delete that releases quota once under concurrent requests, owner/group checks, unit-subject validation and failure cleanup. Images are fully decoded to reject truncated payloads; Word package namespaces, content types and macro indicators are validated.
5. Core interface: centralized API client, reusable forms and countdowns, loading/error/empty states, protected routes, responsive navigation, accounts, onboarding, a deadline-first dashboard backed by real data, subject and unit create/edit/delete, material upload/download/delete, material search/category/subject filters, subject-scoped library links, exams, calendar, reminders and notifications. A shared SVG icon system provides consistent actions and distinct PDF/image/Word indicators. Successful create forms clear their prior values.
6. Exams and reminders: editing, rescheduling, soft deletion, calendar views, global reminder preferences and an independent worker with in-app delivery, optional email, retries, cancellation, deduplication and restart catch-up. Active exams block subject deletion. Soft-deleted exams do not: subject deletion clears their foreign key while preserving the exam rows, reminders, notifications and immutable subject name/code snapshots. A database check constraint prevents active orphan exams. Downgrading below revision `0006` requires resolving archived exams whose former subject was deleted. Tests disable external delivery and use fake providers or the local file sink.
7. Operations: an SQLite backup command packages a hot database snapshot, private uploads and a checksum manifest. A production preflight checks configuration, limits, CORS, account email, upload writability, database access, Alembic head and SQLite foreign keys. PostgreSQL uses `pg_dump` plus a coordinated upload backup.
8. Verification: API workflow and security tests, migration round trips and adoption, main-database preservation, process-restart persistence, TypeScript/build/lint checks and headless Edge workflows all use isolated data where applicable. Exact completed checks and remaining external-system limits are recorded in PROGRESS.md.

## Acceptance workflow

Register -> profile -> subject -> unit -> PDF upload -> library -> authenticated download -> exam -> dashboard countdown -> logout -> login -> persisted records. A second student sees an empty library and receives 404 for the first student's private download. Browser tests also reload the session and check mobile navigation.

## Operations

Follow the exact Windows PowerShell commands in README.md. Local services are FastAPI and Vite; the independent reminder worker is required for scheduled delivery. SQLite and private disk storage are defaults. A stable random secret retains sessions across restart. Production requires migrations, persistent database and upload storage, a public HTTPS frontend URL, explicit HTTPS CORS, Resend-backed verified email, TLS and a suitable reverse proxy. Run the backup before schema changes and run the deployment preflight before starting public traffic.

No AI, chat, material preview/replace UI or advanced collaboration is claimed. Existing group APIs are retained and material authorization is tested; the milestone upload UI creates private files. No public deployment is claimed. Live Resend, PostgreSQL, public TLS/hosting, backup restoration and non-Edge browsers remain outside the completed checks. Actual results and limitations are recorded in PROGRESS.md.
